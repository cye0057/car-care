## 一、缓存一致性

**Q：门店详情加了缓存，怎么保证缓存和数据库一致？**

A：这个场景我选择**不追求强一致**。门店信息是展示型数据，能容忍秒级延迟；强一致的成本（分布式锁、读写同库）远大于收益。具体用 **Cache Aside + 延迟双删**：

```
更新 DB → 删缓存 → sleep 500ms → 再删一次
```

第二次删除是为了解决一个真实竞态：

```
T1 读请求 miss，回源 DB 读到旧值
T2 写事务提交，删缓存
T3 写事务回滚            ← 缓存已经被删了
T4 T1 把旧值写回缓存     ← 脏数据驻留到 TTL 到期
```

延迟的 500ms 不是拍脑袋——取「典型写事务耗时 + 余量」，让 T4 的回填发生在 T2 之后、第二次删除之前。物理 TTL 7 天作为最终兜底。

**追问：为什么不监听 binlog（Canal）？**
那是更彻底的做法，一致性更强，但要引入 Canal 组件、维护订阅位点、处理重复消费和乱序，架构复杂度上一个量级。我的场景是本地服务 + 单机，写 QPS 不高，用延迟双删足够。如果要上多节点且不能容忍任何窗口，我会切 Canal。

**追问：延迟时间怎么确定的？**
取写入事务的典型耗时加余量。本项目写事务都很轻（单表更新），500ms 有余量。如果事务里嵌套 RPC 可能几秒，双删就不够用了，得靠 binlog 或读写同一个存储。这也是双删的固有局限——**它假设第二次删除能追上回填**。

**追问：为什么不用「先更新缓存再更新 DB」？**
那会让不一致窗口变长，而且并发写会互相覆盖，后写的可能被先写的缓存盖掉。业界基本都弃用这个方向。

**加分点**：主动说这是折中，不是最优解，并给出升级路径。

## 二、缓存三件套

**Q：缓存穿透、击穿、雪崩分别怎么防的？**

A：
- **穿透**（查不存在的 id）：空值也缓存，TTL 120s。查一次之后恶意请求直接命中空值，不触 DB
- **击穿**（热点 key 过期瞬间）：**逻辑过期**。`CacheData` 里内嵌 `expireAt`，物理 TTL 给 7 天兜底。逻辑过期时直接返回旧值，只有 1~2 个线程负责异步重建，其余线程零等待
- **雪崩**（大量 key 同时过期）：TTL 加随机抖动，避免集中过期

**追问：逻辑过期为什么允许返回旧值？**
这是主动的取舍——用**短暂不一致**换**零等待**。对比互斥锁阻塞方案：200 个线程同时要等重建完成，RT 直接被拖到重建耗时。我的实测是：删 key 后 200 并发击穿，只有 2 次 DB 回源，均值 RT 13ms、P95 90ms。P95 那个尖峰就是持锁线程重建、其余线程自旋等待的代价，我觉得可以接受。

**追问：那库存、价格这种不能返回旧值的场景怎么办？**
那些不走缓存一致性那套。库存我直接在 Redis 里用 Lua 原子扣，不查缓存；价格如果要求精确，应该读写同一个存储或走 Canal。

**追问：空值缓存会不会让恶意请求把内存打爆？**
会。所以我给空值单独的短 TTL（120s）而不是正式数据的 7 天。生产上还要加布隆过滤器或参数校验做前置拦截。这个我目前是短 TTL 兜底，没有上布隆过滤器。

**加分点**：把「击穿允许不一致」讲成主动取舍而不是缺陷，并给出反例场景（库存/价格）。

## 三、秒杀防超卖

**Q：秒杀怎么保证不超卖？**

A：三道闸门，层层收窄：

```
第 1 道  Redis+Lua 原子预减     —— 毫秒级挡住 99% 的请求
第 2 道  唯一索引 (coupon_id, user_id, type)  —— 挡重复领取
第 3 道  DB 条件扣减 stock > 0  —— 终极兜底，保证不破库存
```

第 1 道用 Lua 脚本把「查库存 + 查重复 + 预减 + 记名」四步合一，在 Redis 单线程内串行执行。实测 300 并发抢 20 库存，成功恰好 20、DB 剩余 0、领券记录 20 条且去重用户 20。售罄后 Redis 库存归 0，Lua 直接拦截，**不再触达数据库**。

**追问：为什么用 Lua 而不是分布式锁？**
分布式锁要经过「加锁 → 执行 → 解锁」三次 Redis 往返，而且锁超时和业务耗时耦合——业务执行超过锁超时就会并发进入，等于没锁。Lua 在 Redis 单线程内天然串行，一次往返就完成，不需要额外的锁生命周期管理。

**追问：Lua 脚本在集群模式下有什么问题？**
多 key 操作会跨 slot，需要 hashtag 把相关 key 强制分到同一 slot，或者接受单节点执行。本项目是单机 Redis 没遇到，但我清楚这个约束。

**追问：Redis 挂了怎么办？**
不会假装没事。Lua 执行失败直接返回失败让用户重试，DB 的条件更新仍然是最后一道防线，**不会破库存**。真正要解决的是降级——缓存不可用时限流保护 DB，宁可让用户等，不能把 MySQL 打挂。

**加分点**：主动说三道闸门是「层层收窄」而不是只有一道，且第 3 道不依赖 Redis 可用。

## 四、消息队列异步化

**Q：为什么抢券要接 MQ 异步落库？**

A：抢券瞬间的写峰很陡，同步写 DB 会让接口 RT 被 DB 写耗时决定，而且数据库会被打爆。改成：Lua 抢到后**发号 + 投递消息立即返回**，落库交给消费者异步做。用户拿到的是一个「排队中」的记录 id，前端短轮询结果。

**追问：消费失败了消息怎么办？**
**手动 ack**。消费成功才 ack，异常就 nack 不重入队（进死信或丢弃并告警）。自动 ack 的话，ack 之后进程崩了消息就丢了。

**追问：重复消费怎么保证幂等？**
唯一索引 `(coupon_id, user_id, type)`。重复消费时插入冲突，捕获异常后**回补库存**然后吞掉这条消息——库存已经被 Lua 预减了，不补就会账实不符。

**追问：什么是毒消息，怎么处理的？**
反序列化失败、字段缺失这种无论重试多少次都不会成功的消息。这种 nack 后**不进重队列**，否则会无限重试把队列堵住。我直接丢弃 + 记日志，不重队。

**追问：消息丢了怎么办？**
严格来说需要事务消息或本地消息表保证「发成功 + 落库成功」原子。我目前是投递后不校验 ack 结果，属于尽力而为。要工业级就得加本地消息表 + 定时补偿。这是我承认的不足之一。

**加分点**：主动区分「重复消费」和「毒消息」两种幂等场景，它们处理方式完全不同。

## 五、超时关单

**Q：订单超时未支付怎么关单？**

A：用 **RabbitMQ 死信队列**，不是定时任务扫全表。

```
下单 → 投递 orderId 到 delay.queue（无消费者，队列级 TTL 10s）
     → TTL 到期经死信交换机转发到 close.queue
     → 关单消费者按状态判断：只有「待支付」才关
```

相比扫表的优势：**DB 零空转扫描**，关单精度等于「投递时刻 + TTL」，不受扫描周期限制。

**追问：TTL 为什么用队列级而不是消息级？**
消息级 TTL 有个坑：**队头阻塞**。如果队首消息还没过期，后续已过期的消息不会被检查，全卡在队头后面。队列级 TTL 没有这个问题，因为所有消息 TTL 相同，单一超时时长场景下也不会乱序。

**追问：已经支付的订单收到关单消息怎么办？**
消费者按状态幂等判断，只有「待支付」才执行关单，其他状态直接跳过。实测：未支付单 14 秒后自动转「已取消（超时未支付，系统自动关闭）」，已支付单收到同一条消息被跳过。

**追问：投递消息的时候订单还没提交，消费者读不到怎么办？**
把 `rabbitTemplate.convertAndSend` 放在**事务方法之外**。这样消费者可见时订单必然已提交。这是很典型的事务边界问题。

**加分点**：事务边界那个点很加分，说明不是只会调 API。

## 六、号段发号

**Q：订单号为什么不用 UUID 或自增？**

A：
- **UUID**：无序，B+ 树页随机插入导致索引分裂，批量写入性能差；而且 UUID 无法从号追溯业务含义
- **自增 id**：暴露业务量，主库挂了就没号
- **号段模式**：一次从 DB 取一段（步长 100），本地内存分配，DB 查询量降两个数量级

**追问：怎么解决「段用完了瞬间阻塞」？**
**双缓冲 + 90% 异步预取**。当前段用到 90% 时才异步拉取下一段，取号时几乎不等待。这样把「段耗尽的毛刺」摊平掉了。

**追问：重启会不会重号？**
不会。当前段已取到的部分在本地，重启后从 DB 拿新段，已发出去的号不会再发。但如果本地段没持久化，重启后那段剩余的号就浪费了——这是可接受的，浪费 < 步长。

**追问：多实例部署怎么保证不冲突？**
DB 里 `t_seq_alloc` 用乐观锁或 `UPDATE ... SET max = max + step` 保证取段互斥，每实例拿到不同区间。

**加分点**：主动提到「浪费 < 步长」这个代价，说明算过账。

## 七、Feed 推拉结合

**Q：Feed 流为什么不直接用推模式？**

A：推模式的写扩散成本随粉丝数线性增长——一个百万粉账号发一条要写一百万次 ZSet。所以我按**粉丝数阈值**自动切换：

```
粉丝数 < 3000 → 推模式：发帖写扩散进粉丝的 feed:inbox:{uid}
粉丝数 ≥ 3000 → 拉模式：只落库，查询时实时查 DB
查询 = 收件箱(推) ∪ 关注大账号(DB拉)  → 按 id 降序合并去重
```

阈值 3000 是配置项 `carcare.feed.push-follower-threshold`。

**追问：阈值怎么定的？**
是工程经验值，没有严格理论依据。真正的定法是做容量规划：算清楚「ZSet 单次 ZADD 耗时 × 粉丝数」的写放大，找到 P99 延迟能接受的临界点。我这里是拍的 3000，并做成可配置项，方便线上调。

**追问：为什么分页不用 offset？**
ZSet 上按 offset 取是 O(N) 偏移，越往后越慢；而且范围边界处理不好会**重叠或漏数据**。我用双游标 `(maxId, beginTime)`，每页 5 条，响应回传 `nextMaxId/nextBeginTime/hasMore`，前端原样回传。实测三页翻到底：`9..5` / `4,3` / 空，无重叠无丢失。

**追问：你遇到过分页 bug 吗？**
遇到过，而且踩过两次：
1. 初版用 `offset + score` 边界叠加，导致**第二页双重跳过**（同一个笔记被跳过两次）返回空 → 改双游标边界包含 + id 过滤
2. 阈值切换后，同一笔记同时出现在收件箱和拉取结果 → 合并层按 id 去重根治

**加分点**：主动讲自己踩过分页边界坑，且能说出根因。分页边界（包含/排除）不定义清楚必然出问题。

## 八、GEO 附近门店

**Q：附近门店怎么实现的？**

A：Redis GEO（底层是 GeoHash + ZSet）。两个关键设计：
1. **启动全量装载** + **写路径实时同步**：门店新增、改坐标、转休息、删除都实时 `GEOADD` / `GEOREMOVE`，不用等下次启动
2. 查询 `GEORADIUS` 按距离升序 + 半径过滤，`O(logN + M)`

**追问：为什么距离不用 Spring Data 返回的 distance？**
踩过坑：`GeoResult.getDistance()` 的单位**随查询单位漂移**，导致距离恒为 0。我改成取回坐标后用 **haversine 公式自算**，单位确定且可测试。实测 7.02 / 8.42km 与 `redis-cli GEORADIUS` 原值一致。

**追问：热榜为什么用定时任务而不是实时算？**
热榜要聚合「近 7 天有效订单 + 评价数」，实时算每次查询都要跨表 JOIN 聚合，代价高。改成 `HotStoreTask` 每分钟 cron 聚合一次重建 ZSet，查询走 `ZREVRANGE` + 阶段 1 的门店缓存，**把实时聚合成本摊平为固定周期刷新**。实测新支付订单在下一分钟边界自动入榜。

**加分点**：主动讲 GeoResult 单位漂移那个坑——说明是真的踩过并验证过。

## 九、WebSocket 集群通知

**Q：集群部署下 WebSocket 怎么把消息送到正确的节点？**

A：**不给网关配会话粘滞**，而是走 Redis Pub/Sub 扇出：

```
任一节点发布 JSON 到 ws:notify
→ 所有节点订阅
→ 每个节点只投递本节点持有的会话
```

新增节点自动加入，无需配置粘性会话。代价是 Redis 多一次扇出，但工单消息量很小，完全可接受。

配套：握手 JWT 鉴权（非法 token 返回 4001 拒绝）、30s 心跳保活、3s 断线重连。

**追问：为什么不用会话粘滞？**
粘性会话要依赖网关配置，连接漂移（节点重启、扩缩容）后就失效，运维成本高。Pub/Sub 方案让「连接在哪个节点」和「消息路由」解耦，天然集群无关。

**追问：你在这个功能上遇到过什么问题？**
`ServerEndpointExporter` 只注册**Spring Bean 的** `@ServerEndpoint` 类，我漏标 `@Component`，导致 `/ws` 根本没注册，请求落到 MVC 报 404，前端触发**重连风暴**。这个 bug 很隐蔽——不会抛异常，就是不生效。

**追问：通知丢了怎么办？**
设计上就是**尽力而为 + 列表兜底**。推送丢失不致命，用户刷新通知列表就能看到。不追求推送的强可靠——那是即时通讯的需求，工单提醒不需要。

**加分点**：主动给出「通知尽力而为 + 列表兜底」的设计取舍，说明区分了不同业务对可靠性的要求。

## 十、压测方法论（很能体现工程素养）

**Q：你的压测数据是怎么得出的？可信吗？**

A：先用一个**方法论声明**说清楚边界，再给数据：

1. **本地 MySQL 主键查询本身 <1ms**，所以「开缓存 vs 关缓存」的 RT 差异只有毫秒级。所以我的核心指标是**数据库实际执行的 SELECT 次数**，不是 RT——5000 请求从 5001 次降到 1 次
2. **不同脚本线程数不同**，QPS 只能在「同请求数」的两两之间比，跨脚本横向比无意义
3. `.jtl` 是**追加写**，重跑前必须删旧文件，否则数据混入

**追问：压测发现过什么功能测试测不出来的问题？**
有，这是压测最大的价值。冷启动 300 并发抢 20 库存，**只成功 13 个而不是 20 个**——丢了 7 个请求。

根因：库存初始化用互斥锁，**未抢到锁的线程空手返回**，导致 Lua 把「key 不存在」误判为售罄。修复为 `setIfAbsent` 原子装载后冷启动并发验证 20/20。

教训是：**空返回 ≠ 业务失败**。这种问题单线程功能测试永远测不出来，只有并发压测才逼得出来。

**追问：还有什么工具链的坑？**
几个：
- JMeter 的 `JSONPostProcessor` 提取 token 失效返回 401 → 改用 CSV Data Set 预注入 300 行 token，避免登录采样器干扰
- Git Bash 里 curl 本地接口必须加 `--noproxy '*'`（本机有 7890 代理变量）
- curl 请求体带中文会被 Git Bash 转 GBK 报 400 → 测试统一用英文 payload
- `grep -c` 计的是**行数**不是出现次数，压缩过的单行 CSS 会让它永远返回 1 或 0——我用它核对组件存在性时误报过一次

**加分点**：主动给方法论边界，比报一个漂亮 QPS 数字可信度高得多。

## 十一、前端（如果你要体现全栈能力）

**Q：前端踩过什么有意思的坑？**

A：一个很典型的——**Vant 4 删除了 `van-banner` 和 `van-avatar` 组件**，但用了**完全不报错**。

表现：横幅文字压住导航栏标题；Feed 页作者头像没有圆形底色框，昵称首字变成裸文本。

根因：Vant 4 已移除这两个组件。用了不报错，而是渲染成一个**空自定义元素**（DOM 节点数为 0、无任何内部结构与样式），子内容失去约束按 static 定位错位。

**关键教训：`npm run build` 通过 ≠ 组件可用。** 构建只能证明模板语法和导入解析正确，不能证明运行时组件存在。

**追问：你怎么查出来的？怎么防止再犯？**
第一版我 `ls node_modules/vant/es` 肉眼比对就下了结论，其实看漏了——`avatar` 根本不在列表里。后来发现**单判据都不够**：
- 只看目录列表 → 我肉眼漏看
- 看 CSS 类名 → 会误报，`van-form` 这类组件的渲染类名不叫 `.van-form`
- 最终用「**目录存在 + `es/index.mjs` 导出**」双判据才准确，19 种组件里确认 2 种缺失

教训：**多判据交叉验证，且要看原始输出而不是扫一眼就下结论。**

## 十二、项目不足与改进（几乎必问）

**Q：这个项目有什么不足？**

A（主动说三点，比被挖出来好）：

1. **单机本地部署，压测数据只能证明方案正确性，不能外推生产容量**。没做过水平扩展验证，不知道 Redis 集群模式下 Lua 的 slot 约束、MySQL 连接池在并发下的表现。这是数据边界，我不会拿它当生产性能承诺。
2. **缓存一致性用的是延迟双删而非 binlog 监听**，是精度和成本的折中。假设了「第二次删除能追上回填」，事务耗时超过 500ms 就失效。
3. **MQ 消息可靠性是尽力而为**——投递后不校验 ack 结果，没有本地消息表 + 定时补偿。抢券成功但消息丢失会导致用户看到「领取成功」但券没到账。工业级要补这一层。

**追问：如果继续优化，你会先做什么？**
优先级：
1. 补 MQ 本地消息表，把「投递成功」变成强保证（影响用户权益，最该先修）
2. 多实例压测，验证号段发号、WebSocket 扇出、Redis 分布式下的真实表现
3. 缓存一致性按数据敏感度分级：展示型继续双删，交易型切 Canal
4. 前端加真正的错误重试与降级 UI（现在依赖 axios 拦截器统一 toast）

**加分点**：按「用户权益影响」排优先级，而不是按技术难度排。

## 十三、常见追问速答（基础但高频）

**Q：ThreadLocal 存用户上下文，会不会内存泄漏？**
会在。ThreadLocal 在 Web 容器线程池场景下，线程不销毁、map entry 不 remove，就会一直被引用。我在**拦截器的 `afterCompletion` 里显式 `remove()`**，保证请求结束清理。

**Q：JWT 无状态，怎么实现主动登出？**
JWT 本身无法主动失效。我用 Redis 存一个黑名单（`logout:token:{jti}`，TTL = token 剩余有效期），拦截器校验时查黑名单。代价是多一次 Redis 查询；量大了可以缩短 token 有效期来缩小黑名单规模。

**Q：为什么用 `@ServerEndpoint` 而不是 Spring 的 WebSocketHandler？**
`@ServerEndpoint` 是标准 JSR-356 注解，配合 `ServerEndpointExporter` 可以把端点注册成 Spring Bean 注入依赖。Spring 的 `WebSocketHandler` 更偏工程化但生命周期管理要自己写。我选前者是为了能注入 Service。踩过的坑就是它必须标 `@Component` 才会被注册。

**Q：订单状态机怎么保证流转合法？**
状态流转走统一 `changeStatus`，每次转移前校验「当前状态 → 目标状态」是否在白名单里（1→5 / 2→3 / 3→4 / 4→6），非法流转直接抛异常。配合条件 UPDATE 防止并发覆盖。

**Q：事务怎么用的？异常会不会不回滚？**
Spring 默认只对 `RuntimeException` 回滚。我在 Service 层加了 `@Transactional(rollbackFor = Exception.class)`，确保检查异常也回滚。另外注意把 `rabbitTemplate.convertAndSend` 放在事务方法之外，避免消息先于事务提交被消费者读到。

## 十四、文件上传与第三方支付（OSS + 支付宝沙箱）

**Q：图片上传是怎么做的？为什么走后端中转？**

A：统一 `POST /api/upload`（multipart）：登录拦截复用鉴权 → 服务端校验图片类型与 ≤5MB → 按 `car-care/yyyy/MM/uuid.ext` 日期分片命名 → 阿里云 OSS SDK `putObject` → 返回公网 URL 落库。管理端（门店封面/项目图）和车主端（笔记晒图/头像）共用一个接口。不走前端直传是因为直传要多一个 STS 临时凭证签发与桶权限设计，毕设规模后端中转更简单可控，且校验、鉴权、命名策略都收在服务端。

**追问：文件名为什么用 UUID 拼日期目录？**
哈希打散 vs 日期目录：日期目录便于按天清理与追溯，UUID 避免重名覆盖和撞名猜 URL。同一天文件都落在同一前缀下，OSS 的 GetBucketLifecycle 规则可以直接按前缀设过期。

**追问：5MB 限制和类型校验放后端够吗？**
不够，只是服务端兜底。严谨做法前端先校验拦截明显非法输入，OSS 侧再配 bucket 策略（仅允许 `image/*`、限制文件大小）做最后一道闸门，三处校验职责不同。

**Q：支付宝支付怎么接的？回调怎么保证安全？**

A：`POST /api/orders/{id}/pay` 校验订单归属 + 待支付状态后，用官方 SDK 构造 wap 下单请求（out_trade_no=orderNo、total_amount、notify_url），返回沙箱收银台跳转 URL；前端新窗口打开。**支付结果只信异步回调**：支付宝 POST 到 `/api/notify/alipay`（该路径在拦截器里显式放行，因为回调没有我们的 token），用 `AlipaySignature.rsaCheckV1` 验签（防伪造通知）→ `TRADE_SUCCESS` 才按 `out_trade_no` 查单 → 状态机 1→2、写 checkoutTime → 返回纯文本 `success`（否则支付宝会按失败重试）。

**追问：回调重复通知怎么办？**
幂等：`paySuccessByOrderNo` 里已支付（status=2）直接忽略，重复通知不重复扣状态、不重复写时间。支付宝本身也会对未收到 `success` 的通知重试多次，所以回调处理必须幂等。

**追问：为什么回调路径要放行登录拦截？**
支付宝服务器回调不带我们签发的 JWT token，拦截器会 401 拒绝。放行后安全性完全由验签承担——验签不通过直接返回 `failure`，不进入业务逻辑。

**追问：沙箱和正式环境的差别？**
只差三个配置：网关 `openapi-sandbox.dl.alipaydev.com → openapi.alipay.com`、沙箱 AppID → 正式 AppID、notify-url 从内网穿透地址换成正式域名。SDK 用法、签名算法、回调协议完全一致，代码无需改动。

## 十五、面试节奏建议

1. **先说架构再深入**：用 30 秒讲清「读写分离思路 + 三个高并发场景」，别一上来就报细节
2. **主动给边界**：每次给数字都带一句「这是本地单机压测」，反而显得严谨
3. **把 bug 当亮点**：`13 → 20`、`van-avatar`、`GeoResult 单位漂移` 这三个都是「只有真的做了才会遇到」的故事，比背八股有说服力
4. **准备好被打断**：面试官常在你说「压测」时打断追问方法学，所以方法论声明要放在数据之前
5. **承认不足时要给方案**：每个不足后面跟一句「如果要改，我会……」
