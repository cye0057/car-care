## 一、演进路径：为什么是这个顺序

技术点的叠加顺序不是随意的——**每一层都建立在前一层已稳定的业务基线上**，且每个技术点都能独立演示、独立压测。

```
阶段 0 基础框架          没有稳定的 CRUD 与状态机，谈不上性能优化
   │  产出：14 表 + 订单状态机 + 管理台
   ▼
阶段 1 缓存体系          先证明「读路径」能被保护 —— 这是后续一切读优化的前提
   │  产出：99.98% 读放大降低
   ▼
阶段 2 秒杀 + MQ         缓存解决读，MQ 解决写峰 —— 读写分离的完整闭环
   │  产出：0 超卖 0 重复 0 丢失
   ▼
阶段 3 GEO + 热榜        在缓存成熟后做新读场景，验证「复杂数据结构」能力
   │  产出：GEO 检索 + ZSet 榜单
   ▼
阶段 4 Feed 流           推拉结合是本项目最复杂的设计，需要前面全部基础设施
   │  产出：双游标分页 + 双模式
   ▼
阶段 5 用户端 + 通知      把后端能力真正暴露成可用产品，补实时通道
   │  产出：Vant H5 全链路 + WebSocket 集群通知
   ▼
阶段 6 打磨              把上面六步沉淀成可讲、可查、可复测的文档
   ▼
阶段 7 上传 + 支付       补齐产品的两个"硬能力"：文件存储与真实支付通道
   │  产出：OSS 图片上传 + 支付宝沙箱支付 + 用户头像 + 车主注册 + 车辆档案管理
```

关键原则：**每阶段结束系统都处于可运行状态**。阶段 0 只实现核心 CRUD，其余接口随各阶段填充——避免「写完一半跑不起来」的返工。

## 二、核心设计取舍（面试高频）

### 2.1 缓存一致性：为什么用延迟双删而不是只删缓存

常规实现「更新 DB 后删缓存」存在经典竞态：

```
T1: 读请求发现缓存 miss，回源 DB 读到旧值
T2: 写事务提交新值，删除缓存
T3: 写事务回滚 ← 此时缓存已被删
T4: T1 把旧值写回缓存   ← 脏数据驻留至 TTL 到期
```

本项目采用 **写 DB → 删缓存 → 延迟 N ms → 再删一次**，第二次删除清掉 T4 回填的脏值。配套 `CacheHelper`：`SETNX` 互斥锁 + **Lua 安全解锁**（防止误删他人的锁）+ 500ms 延迟双删。

### 2.2 击穿防护：为什么用逻辑过期而不是阻塞等待

| 方案 | 特点 |
|---|---|
| 互斥锁 + 阻塞等待 | 简单，但 200 个线程同时阻塞，RT 被拖到重建耗时 |
| **逻辑过期（本项目）** | `CacheData` 内嵌 `expireAt`，未到期直接返回旧值，仅 1~2 线程异步重建。以**短暂不一致**换**零等待** |
| 互斥锁 + 空值返回 | 兼顾两者，作为兜底 |

本项目两者结合：逻辑过期扛住绝大多数击穿，`SETNX` 互斥锁 + 物理 TTL 7 天作为兜底。压测证据：200 并发击穿只有 2 次 DB 回源。

### 2.3 秒杀：为什么用 Lua 而不是分布式锁

Redisson 分布式锁要经过「加锁→执行→解锁」三次 Redis 往返，且锁超时与业务耗时耦合。**Lua 脚本在 Redis 单线程内串行执行**，天然无锁且一次往返，把「查库存 + 查重复 + 预减 + 记名」四步原子化。

三道闸门防超卖：

```
第 1 道  Redis+Lua 原子预减      —— 挡住 99% 的请求，毫秒级
第 2 道  t_coupon_order 唯一索引  —— (coupon_id, user_id, type) 挡重复领
第 3 道  DB 条件扣减 stock>0     —— 终极兜底，保证不破库存
```

落库失败自动**补偿回滚 Redis**，避免「Redis 已扣但 DB 无记录」的库存幽灵。

### 2.4 超时关单：为什么用死信队列而不是定时扫表

| 方案 | 问题 |
|---|---|
| 定时任务扫全表 | 每几分钟全表扫描，DB 空转；关单精度受扫描周期限制（可能超卖窗口） |
| **RabbitMQ 死信队列（本项目）** | 下单即投递 TTL 队列，到期经死信交换机进入关单队列。**DB 零空转**，关单精度 = 投递时刻 + TTL |

实现细节：TTL 用**队列级而非消息级**——消息级 TTL 在队首未过期时会阻塞后续过期检查（队头阻塞）。单一超时时长场景下队列级 TTL 无乱序问题。演示 TTL 10s，生产 30 分钟。

消费者按状态判断幂等：**仅待支付才关**，已支付单收到关单消息直接跳过。

### 2.5 号段发号：为什么不用 UUID 或自增

```
UUID    → 无序，B+ 页随机插入，索引分裂，批量写入性能差
自增 id → 暴露业务量，且主库挂了就没号
号段    → 一次取一段（步长 100），本地分配，DB 查询量降两个数量级
```

`SegmentService` 采用**双缓冲 + 90% 异步预取**：当前段用到 90% 时才异步拉取下一段，取号时几乎不等待，消除「段耗尽瞬间的取号毛刺」。压测号段 1001~1041 单调递增无冲突。

### 2.6 Feed：为什么推拉结合

单一推模式在大 V 场景写扩散成本失控（1 个百万粉账号发 1 帖要写 100 万次 ZSet）。本项目按粉丝数阈值（`carcare.feed.push-follower-threshold`，默认 3000）自动切换：

```
粉丝数 < 阈值 → 推模式：发帖时写扩散进每个粉丝的 feed:inbox:{uid}
粉丝数 ≥ 阈值 → 拉模式：发帖只落库，查询时实时查 DB
查询 = 收件箱(推) ∪ 关注大账号(DB拉)  → 按 id 降序合并去重
```

**双游标分页**用 `(maxId, beginTime)` 替代 offset——offset 深分页在 ZSet 上是 O(N) 偏移，且边界重叠会导致漏数据。每页 5 条，响应回传 `nextMaxId/nextBeginTime/hasMore`，前端原样回传。

### 2.7 WebSocket 集群通知：为什么用 Redis Pub/Sub 而不是会话粘滞

集群部署下，WebSocket 连接落在哪个节点，消息就必须路由到哪个节点。两种做法：

| 方案 | 代价 |
|---|---|
| 网关会话粘滞 | 引入粘性会话配置，连接漂移后失效 |
| **Redis Pub/Sub 扇出（本项目）** | 任何节点发布到 `ws:notify`，所有节点订阅后只投递本节点持有的会话。**集群无关** |

配套：握手 JWT 鉴权（非法 token 4001 拒绝）、30s 心跳保活、3s 断线重连。设计取舍是**通知尽力而为 + 列表兜底**——推送丢失不致命，用户仍可刷新通知列表。

### 2.8 支付：为什么选支付宝沙箱而不是微信支付或模拟支付

| 方案 | 门槛 | 结论 |
|---|---|---|
| 微信支付 V3 | 需真实商户号（企业/个体户资质）、API 证书、公网回调 | 个人毕设阶段拿不到商户号，先记录方案待后续 |
| **支付宝沙箱（本项目）** | 开放平台申请沙箱应用，秒开，AppID+应用私钥+支付宝公钥即可 | 完整走「下单→收银台→异步回调→状态机」真实链路，与正式环境仅网关地址不同 |
| 模拟支付（初版） | 零依赖 | 只演示状态机 1→2，无真实支付流程 |

落地时保留了一个关键的正规设计：**支付结果只信异步回调**。前端跳收银台成功 ≠ 支付成功，订单置已支付必须由 `/api/notify/alipay` 回调触发——回调里 `rsaCheckV1` 验签（防止伪造通知）、按 `out_trade_no` 查单、`TRADE_SUCCESS` 才流转、已支付幂等忽略（重复通知不重复处理）。

### 2.9 图片上传：为什么走后端中转而不是前端直传 OSS

| 方案 | 权衡 |
|---|---|
| 前端直传（STS 临时凭证） | 流量绕过服务器、扩展性好，但要多一个 STS 签发环节与桶权限策略设计 |
| **后端中转（本项目）** | 上传接口统一走登录拦截（鉴权复用）、服务端做类型/大小校验与日期分片命名，毕设规模下实现简单可控 |

同一套 `/api/upload` 供管理端（门店封面、项目图）与车主端（笔记晒图、头像）复用，返回公网 URL 落库，前端只存 URL 不接触字节流。

## 三、踩坑复盘（最有价值的部分）

> 判断标准：这些问题如果只写代码不做并发压测、不升级依赖、不上集群，**永远不会被发现**。

### 3.1 只有并发压测才能暴露的竞态

**库存初始化丢 7 个请求**（阶段 2）
- 现象：冷启动 300 并发抢 20 库存，只成功 13 个
- 根因：库存初始化用互斥锁，未抢到锁的线程**空手返回**，Lua 把「key 不存在」误判为售罄
- 修复：改 `setIfAbsent` 原子装载，冷启动并发验证 20/20 无丢失
- 教训：**空返回 ≠ 业务失败**。压测对比数据（13 → 20）就是最有力的证据

### 3.2 只在做版本升级时才会踩的坑

**Vant 4 删除了 `van-banner` 和 `van-avatar`**（阶段 5-下）
- 现象：横幅文字压住导航栏标题；Feed 流作者头像没有圆形底色框，昵称首字变成裸文本
- 根因：Vant 4 已移除这两个组件，用了**不报错**，而是渲染成一个空自定义元素（`.van-banner` 节点数为 0、无任何内部 DOM 与样式），子内容失去约束按 static 定位错位
- 修复：两处都改自定义 div 实现；全项目 **19 种**组件逐个核对
- 教训：**构建通过不代表组件存在**。UI 库跨大版本升级后必须核对组件清单

> 核对方法演进（值得记录）：第一版只 `ls node_modules/vant/es` 看目录，肉眼比对后误判"全部对上"——其实 `avatar` 根本不在目录列表里，是我看漏了。后来发现单判据不够：`van-form`/`van-date-picker` 目录和导出都在、但渲染出的类名不叫 `.van-form`，用 CSS 类名做判据会误报。最终用「目录存在 + `es/index.mjs` 导出」双判据才准确。**多判据交叉验证，且要看原始输出而不是扫一眼结论。**

### 3.3 只在集群/测试隔离时才暴露的问题

**`ServerEndpointExporter` 与 `@ServerEndpoint`**（阶段 5-上）
- 现象：`/ws` 返回 404，前端触发重连风暴
- 根因：`ServerEndpointExporter` 只注册**Spring Bean 的** `@ServerEndpoint` 类，漏标 `@Component` 导致端点根本没注册，请求落到 MVC
- 连带问题：该 Bean 在 `webEnvironment=NONE` 的单元测试上下文里炸（`ServerContainer not available`）→ 用 `@ConditionalOnWebApplication(SERVLET)` 隔离，恢复了用户写的 `SegmentServiceTest` 3/3

### 3.4 编码坑：平台默认字符集

**Redis 订阅中文乱码**（阶段 5-上）
- 根因：`new String(bytes)` 在 Windows 上用默认 GBK 解码 UTF-8 字节
- 修复：显式 `StandardCharsets.UTF_8`
- 教训：**任何跨边界的数据传输（MQ、Redis、HTTP、WebSocket）都要显式指定字符集**，不要依赖 JVM 默认值

### 3.5 边界叠加导致的分页错乱

**Feed 第二页返回空**（阶段 4）
- 根因：`offset + score` 边界叠加，同一个笔记被跳过两次
- 修复：双游标边界包含 + id 过滤去重
- 连带 bug：阈值切换后同一笔记同时出现在收件箱与拉取结果 → 合并层按 id 去重根治

**两个分页 bug 的共性：用「范围边界 + 游标」时，边界是包含还是排除必须明确定义并用测试锁死。**

### 3.6 环境与工具链坑

| 坑 | 现象 | 解法 |
|---|---|---|
| Git Bash 代理变量 | curl 本地接口超时/502 | 加 `--noproxy '*'` |
| Git Bash 中文转码 | curl 请求体带中文报 400 | 测试用英文 payload |
| JMeter jtl 追加写 | 重跑数据混入，结论错误 | 重跑前 `del *.jtl` |
| Spring Data 距离单位漂移 | `GeoResult.getDistance()` 恒为 0 | 取回坐标用 haversine 自算 |
| JMeter token 提取失效 | JSONPostProcessor 返回 401 | 改 CSV Data Set 预注入 token |
| 重跑建库脚本 | 丢手工插入的 order 行 | 号段种子补进 `phase2_seckill.sql`，`SegmentService` 对缺行抛带指引的异常 |
| MySQL 服务名误记 | `net start MySQL80` 报拒绝访问 | 实际服务名是 `MySQL`，`MySQL80` 是残留未使用服务 |
| Redis 地址过时 | `Unable to connect to Redis` | 虚拟机换网段后配置 IP 失效，用 `redis-cli` 逐个网段探测定位 |
| RabbitMQ 长期不启动 | 后端跑了 3h17m、累积 4452 次连接错误后 exit code 1 | 启动不受影响（AMQP 惰性），但 `SimpleMessageListenerContainer` 持续重试重声明 auto-delete 队列最终导致上下文失败；长时间运行必须起 RabbitMQ |
| Maven 参数位置错 | `Unrecognized option: --spring.xxx` | 应用参数用 `spring-boot.run.arguments`，`jvmArguments` 是 JVM 参数位 |
| `grep -c` 计数 | 压缩过的单行 CSS 永远返回 1 或 0 | 它计的是**行数**不是出现次数，数出现次数要 `grep -o \| wc -l` |
| Git Bash 下 Python 相对路径 | `os.path.isdir` 返回 False | Python 走 Windows CWD，与 Git Bash 翻译后的路径不一致，一律用绝对路径 |
| 第三方 SDK 版本号不存在 | Maven 报 `Could not find artifact ... in aliyunmaven` | 凭记忆写的 `alipay-sdk-java 4.39.26.ALL` 镜像里没有；查 `maven.aliyun.com/repository/public/.../maven-metadata.xml` 取真实版本（本用 4.40.996.ALL） |
