### 单点完整版

**缓存一致性**
> 针对读多写少场景设计 Redis 缓存：逻辑过期 + SETNX 互斥锁防击穿、空值缓存防穿透、TTL 随机抖动防雪崩，写路径 Cache Aside + Lua 安全解锁 + 500ms 延迟双删解决「删缓存后并发读回填旧值」竞态。JMeter 压测 5000 请求下数据库查询从 5001 次降至 1 次（99.98%），吞吐从 508 提升至 1018 QPS。

**秒杀防超卖**
> 设计 Redis+Lua 原子脚本将「查库存+查重复+预减+记名」四步合一在 Redis 单线程内串行执行，天然无锁且一次往返；唯一索引 (coupon_id,user_id,type) 与 DB 条件扣减 `stock>0` 构成二、三道闸门；MQ 投递失败同步回滚 Redis 预减，保证用户资格不被白扣。冷启动 300 并发抢 20 库存，成功恰好 20、DB 剩余 0，0 超卖 0 重复。

**消息队列异步化**
> 抢券成功后发号 + 投递消息立即返回，消费者手动 ack 落库实现削峰；幂等靠唯一索引冲突后回补库存并吞掉，毒消息 nack 不进重队列做隔离；订单超时关闭用队列级 TTL + 死信交换机替代定时任务扫全表，DB 零空转，关单精度等于投递时刻加 TTL。

**附近门店与热度榜**
> Redis GEO 存门店坐标（启动 `ApplicationRunner` 全量装载 + 门店增删改实时同步 geoAdd/geoRemove），按半径升序检索；距离用 haversine 自算，规避 Spring Data `Distance` 单位随版本漂移。热度榜由 ZSet 聚合近 7 天有效订单 + 评价，`HotStoreTask` 定时全量重建（聚合幂等，多实例重复执行无害）。

**车主社区动态（Feed 推拉结合）**
> 车主发养车笔记后写扩散进粉丝收件箱 ZSet，粉丝数超阈值（默认 3000）自动切拉模式；查询合并收件箱与 DB 拉取，按 id 降序去重；分页用双游标 (maxId, beginTime) 替代 offset，规避 ZSet 深分页 O(N) 与边界重叠漏数据。

**实时通知（集群）**
> 工单动态经 Redis Pub/Sub 发布到 `ws:notify`，各节点订阅后仅投递本节点持有的 WebSocket 会话，新增节点自动加入、无需会话粘滞配置；握手 JWT 鉴权、前端 30s 心跳保活 + 3s 断线重连。

**文件上传（阿里云 OSS）**
> 设计统一图片上传接口 `POST /api/upload`：登录拦截复用鉴权，服务端校验图片类型与 ≤5MB，按 `car-care/yyyy/MM/uuid.ext` 日期分片命名存 OSS，返回公网 URL 落库；管理端（门店封面/项目图）与车主端（笔记晒图/头像）共用一个接口，前端只存 URL 不接触字节流。

**第三方支付（支付宝沙箱）**
> 订单支付接入支付宝 wap 下单：下单返回沙箱收银台跳转 URL，支付结果只信异步回调——`/api/notify/alipay` 用 `rsaCheckV1` 验签防伪造通知，`TRADE_SUCCESS` 才按 `out_trade_no` 幂等驱动订单状态机 1→2（重复通知不重复处理）；回调路径放行登录拦截。

**AI 助手（LangChain Agent + RAG + SSE 流式）**
> 独立设计并实现 AI 养车顾问：Python 侧用 LangChain 1.2 `create_agent` 编排 11 个工具（门店/项目/套餐/券检索、用户车辆与订单上下文、保养知识 RAG、预约草稿生成），Chroma + bge-m3 做向量检索，检索阈值按实测分数分布标定为 0.35（相关问题 0.43~0.68 / 无关 0.18~0.25）；Java 侧只做唯一网关，用 `WebClient` + `Flux` 逐帧透传 SSE（客户端断连时 Reactor 自动取消订阅并中止上游生成，无需手写取消逻辑），落库走独立有界线程池避免阻塞事件循环。
> **架构上的关键取舍**：AI 服务完全无状态（会话历史存 Java 的 MySQL，每次随请求下发），只绑 `127.0.0.1` 并用内部令牌二次校验；用户私有数据由 Java 按 JWT 身份裁剪后下发，AI 服务没有任何「按 userId 查数据」的入口——越权在结构上不成立，7 条越权路径实测全部拦截，AI 服务停掉也不影响下单支付主链路。
> **踩坑与实测**：定位并修复了 SSE 流式下的两个真实 bug（工具调用分片按 index 累积导致跨轮串味、过渡语泄漏进最终回答，均补了回归测试）；用 `dynamic_prompt` 中间件注入当天日期解决模型编造过期预约日期；JMeter 100 并发长连接实测 0 断流 0 错误、495 次请求落库零丢失，并通过「同一脚本交替打 Java 网关与直连 Python」的对照实验把瓶颈定位于上游模型（模型调用自身 1.1s → 2.6s）而非本项目代码。

## 三、STAR 项目描述模板（面试口述用）

**Situation**：以维修保养为核心业务域做本地车主服务平台，基础 CRUD 跑通后需要叠加高并发场景，目标不是堆技术，而是每个技术点都能量化证明。

**Task**：让「读多写少」「瞬时写峰」「实时推送」三个典型场景都有可验证的优化方案，而不是纸上谈兵。

**Action**：
- 缓存：逻辑过期扛住绝大多数击穿（200 并发只 2 次回源），SETNX 互斥锁 + 物理 TTL 兜底，延迟双删解决回滚竞态
- 秒杀：Lua 单线程串行化免锁，三道闸门防超卖，MQ 异步落库把写峰削掉，死信队列替代扫表关单
- Feed：按粉丝阈值推拉切换，双游标分页
- 通知：Redis Pub/Sub 扇出，让 WebSocket 与节点拓扑解耦
- AI：Java 只做网关与鉴权，Python 侧无状态跑 Agent；用户私有数据按身份裁剪下发，越权在结构上不成立

**Result**：
- 数据库读放大降低 99.98%（5001→1 次 SELECT），同请求数吞吐 2.0x
- 300 并发抢 20 库存：0 超卖、0 重复、0 丢失
- 压测反向暴露了一个功能测试测不出来的 bug：库存初始化用互斥锁导致冷启动丢 7 个请求（成功数 13 而非 20），改成 `setIfAbsent` 原子装载后 20/20
- AI 助手 100 并发长连接：0 断流、0 错误、落库零丢失；用「同脚本交替打网关与直连服务」的对照实验把瓶颈定位于上游模型而非自己的代码

**为什么这条 Action 值得讲**：压测不是走流程，而是真的把并发竞态逼出来了。

## 五、不要说的话（诚实边界）

面试最容易翻车的是夸大。这些别主动说：

- ❌ 「QPS 提升了 10 倍」——本地 MySQL 主键查询本身 <1ms，RT 差异只有毫秒级。真实收益是**数据库读保护**，别说 RT
- ❌ 「扛住了上万并发」——最大压测是 300 并发。就说 300 并发
- ❌ 「做到了最终一致性」——延迟双删是近似手段，是精度与成本的折中，不是强一致
- ❌ 「生产环境部署过」——单机本地部署，MySQL/Redis/RabbitMQ 都在本机或虚拟机，没有真实集群
- ❌ 「缓存零不一致」——逻辑过期就是允许秒级不一致，换的是零等待
- ❌ 「AI 扛住了高并发」——只测到 100 并发且仍 0 错误就停了，**第一个出错点在哪并不知道**；而且延迟大头是上游模型的 2.6s，不是本项目的吞吐能力。就说「100 并发长连接 0 断流 0 丢失」
- ❌ 「AI 能自动下单」——AI 只产出预约草稿，真实下单仍走既有的 `POST /api/orders`，用户确认后才落库，库存与优惠券校验口径不重复实现
- ❌ 「RAG 检索很准」——5 篇语料是手写的，阈值 0.35 是在这个语料集上标定的，换 embedding 模型或大改语料必须重新标定

被问到容量问题时，主动给边界比硬撑可信度高得多。
