# AI 养车顾问模块 · 设计说明

阶段 8 新增。本文只写**为什么这么做**和**踩过什么坑**——代码怎么读请看
`car-care-ai/README.md`，接口清单看 Swagger 的 `18-AI助手` 与 `97-AI内部接口` 分组。

- 新增代码：Java 21 个文件 / 1796 行，Python 24 个文件 / 1821 行（含脚本），前端 3 个文件 / 465 行
- 新增数据表：2 张（`t_ai_conversation`、`t_ai_message`）

## 一、整体链路

```
car-care-app 聊天页
   │  POST /api/ai/chat  (token 头, text/event-stream)
   ▼
car-care-server :8082          ← 唯一网关 / 唯一鉴权点
   ├─ LoginInterceptor         → BaseContext.getUserId()
   ├─ AiContextService         → 按 JWT 身份裁剪用户上下文（车辆/订单/工单/券）
   ├─ AiConversationService    → 会话与历史的唯一数据源（MySQL）
   ├─ AiChatService            → WebClient 调 Python，Flux 逐帧透传，收尾异步落库
   └─ /api/internal/ai/**      ← 内部令牌，只读公共目录
                    ▲
                    │ httpx（X-Internal-Token）
                    │
car-care-ai :8000  │
   ├─ LangChain create_agent + 11 个工具
   ├─ Chroma + bge-m3（RAG）
   └─ 完全无状态：不连业务库、不存会话
```

## 二、四个关键决策

### 1. Java 是唯一网关，Python 不对外暴露

前端只认 car-care 的 JWT，永远拿不到 AI 服务的地址。AI 服务只绑 `127.0.0.1`，
再加一道 `X-Internal-Token` 共享令牌。

为什么不直接让前端连 Python：AI 服务一旦对外，就得在 Python 侧重新实现一套鉴权、CORS、
限流和会话归属校验——那是把 Java 已经做好的事做第二遍，而且两套鉴权的失效边界很难对齐。

**代价**：Java 成了单点，多一跳网络开销（本机调用，可忽略）。

### 2. Python 完全无状态，历史由 Java 下发

会话历史存在 Java 的 MySQL 里，每次对话请求把最近 6 轮历史随请求发过去。Python 不存任何会话。

三个好处：

1. **归属校验只有一处**。会话属于谁的判断复用 `userId`，不存在「AI 服务记错用户」的可能；
2. **Python 可以随时重启、可以水平扩容**，不需要会话粘性，也不需要引入 Redis/Postgres checkpointer
   这类外部状态存储；
3. **对话记录留在业务库里**，后台可以直接查、可以做效果评估，不用再去 Python 侧捞。

**代价**：每轮多一次「读历史」的查询（sessionId 上有索引，可忽略），
且没法用 LangGraph checkpointer 的跨轮状态能力（比如跨轮的待办事项）。

**为什么不顺手用 LangGraph 的 checkpointer**：练习项目里用过 `InMemorySaver` / `PostgresSaver`，
它们解决的是「让 Agent 记住上下文」。但这里上下文已经由 Java 提供了，
再引入一层 checkpointer 等于同一份会话存两处，还得处理两边不一致的问题。

### 3. 数据双通道：私有数据下发，公共数据走内部接口

用户私有数据（车辆、订单、工单、已领券）由 Java 用**已通过 JWT 校验的 userId** 查好后，
裁剪成精简视图随请求下发。AI 服务没有任何「按 userId 查数据」的入口。

公共目录数据（门店、项目、套餐、可抢券）由 Python 调 Java 的内部只读接口拿。

这样分的理由：

- **越权在结构上不成立**。AI 服务就算被人拿到内部令牌，也只能查「营业中的门店」这类公开数据，
  没有读取他人订单的通道。这比「在 Python 侧写校验逻辑」可靠得多——校验逻辑可能被绕过或有 bug，
  没有入口则无从绕过；
- **过滤口径只有一份**。门店「营业中」、项目「在售」的判定留在 Java，
  Python 不会出现「用另一套条件查出来不该卖的东西」；
- **顺带继承了缓存**。内部接口复用 `StoreService.listEnabled()`，
  所以 AI 的高频查询直接命中阶段 1 的 Redis 缓存，不打 MySQL。

内部接口刻意**不提供**任何按 userId 查询的接口——这是设计约束，不是遗漏。

### 4. 超时预算分层：上游先认输

| 层级 | 值 | 含义 |
|---|---|---|
| Java → Python 建连 | 3s | AI 服务在本机，3 秒连不上就是没起来，快速失败 |
| Java → Python 空闲读 | 180s | reactor-netty 的 `responseTimeout`，是**两次数据之间的最大间隔**，不是总时长 |
| Python 单请求总预算 | 120s | `asyncio.timeout` 硬预算，超时主动推 error 事件 |

关键点是 **Python 的 120s < Java 的 180s**：让上游自己认输并给出友好提示，
而不是下游先掐断、上游还在继续烧 token。

`travel-java-server` 踩过这个坑：SseEmitter 超时 180s，但工具轮数 3 × 上游读超时 120s
最坏能到 360s+，结果客户端看到截断的流，而 worker 线程还在跑。

## 三、过渡语处理（reset 事件）

模型在调工具前常先说一句「让我查一下门店」。这句话不该留在最终回答里。

三种做法：

| 做法 | 问题 |
|---|---|
| 直接透传 | 用户会看到「让我查一下…」残留在回答开头 |
| 攒完整段再推 | 首字延迟 = 完整生成时间，打字机效果消失（travel 项目的选择） |
| **透传 + reset** | 先把 `delta` 正常推给前端；一旦发现这一轮出现工具调用，立刻发 `reset` 让前端清掉 |

选了第三种：既保住真流式，又不会把中间态留在最终回答里。代价是前端要支持一个 `reset` 事件
（3 行代码）。

**踩的坑**（两个，都写成了回归测试）：

1. 第一版用了一个 `round_has_tools` 布尔标志判断「本轮是否已调工具」，置位后**不复位**。
   于是第二轮之后的过渡语再也不会被清掉，最终回答里堆满了英文自述
   （"I found the store and the item. Let me check the packages..."）。
2. 修完第一个坑后更严重了：最终回答**全是**过渡语。根因是工具调用分片按 **index** 累积，
   而每一轮的 index 都从 0 重新开始——第二轮的调用撞上了第一轮 `pending_calls` 里的残留，
   `first_name` 判不出来，于是 `reset` 和 `tool_start` 都不再触发。

修法：按**工具调用 id** 做键（每轮 id 都不同），并在收到 `ToolMessage` 时清空累积状态。

教训：`stream_mode="messages"` 的流里，index 只在**单轮内**唯一，不是全局唯一。

## 四、RAG 的几个具体选择

### 切分：按 `## ` 章节切，不是按字数切

养车知识天然按「机油/轮胎/刹车」分节。按标题切比按固定字数硬切更不容易把一条完整规则拆散。
只有超长章节才走 `RecursiveCharacterTextSplitter`，分隔符按中文标点优先。

### 每个分片拼 `【文档·章节】` 前缀

前缀同样参与向量化。实测能提升召回：用户问「刹车片多久换」时，
带主题前缀的分片比裸正文更容易被选中。这个做法沿用自 `travel-java-server` 的验证结论。

### 阈值是实测标定的，不是抄来的

用 `GET /v1/rag/search` 观察真实分布：

| 类别 | 分数区间 |
|---|---|
| 相关问题命中 | 0.43 ~ 0.68 |
| 无关问题命中 | 0.18 ~ 0.25 |

取 **0.35** 落在两簇之间的空档。标定过程中发现一个反例：问「安心保返修政策是什么」时，
那条平台规则只拿到 0.428 分——如果照搬 travel 项目的 0.6 阈值，这条正确答案会被直接滤掉。

**换 embedding 模型或大改语料后必须重新标定**，这条写在了 `.env.example` 的注释里。

### 降级：向量库挂了只损失 RAG 能力

`store.py` 里所有检索路径都是 try/except → 返回空列表。Chroma 或 embedding 接口挂了，
对话本身必须继续可用，只是回答里少一层知识库支撑。

## 五、Java 侧的几个实现细节

### 为什么加 webflux：为了拿到 WebClient

pom 里加了 `spring-boot-starter-webflux`，但**服务端仍然是 Tomcat**：
`spring-boot-starter-web` 同时存在时 Spring Boot 判定为 SERVLET 应用，WebFlux 不接管请求处理。
所以 `WebSocketConfig` 上的 `@ConditionalOnWebApplication(SERVLET)` 照常生效，
现有 4 个测试全部通过（其中 `SegmentServiceTest.continuityAcrossSegments` 曾约 1/9 概率偶发失败，
与本模块无关，已按组件真实契约修正断言，根因未定位——见 `PLAN.md` 2026-09-24 补记）。

用 WebClient 换来的收益：客户端断连时 Reactor 自动取消订阅 → WebClient 中止上游请求 →
Python 侧收到 `CancelledError` → 停止模型生成。整条链路自动传导，不用手写取消逻辑。

### 流式透传的两个坑

**坑一：SSE 帧格式。** 原以为 Spring MVC 对 `Flux<String>` 是原样写出，所以自己拼了
`"data: " + json + "\n\n"`。实测（curl 看原始字节）发现 Spring 会按 SSE 规范二次包装：
自动加 `data:` 前缀、元素内部的换行逐行加前缀、末尾补空行。结果是 `data:data: {...}`。

修法：**只返回裸 JSON**，包装交给 Spring。这个结论写在了 `AiChatService.frame()` 的注释里，
因为它违反直觉。

**坑二：`LocalDateTime` 被序列化成数组。** Java 侧组装好用户上下文后，Python 返回 422：

```
Input should be a valid string
loc: ('body', 'userContext', 'vehicles', 0, 'nextMaintainDate')
input: [2026, 10, 20]
```

根因是 `WebClient.builder()` 用的是**裸的 Jackson 编码器**，不读 Spring 容器里那个
配置过的 `ObjectMapper`，于是 `WRITE_DATES_AS_TIMESTAMPS` 生效，日期变成 `[2026,10,20]`。

两处修：一是把容器里的 `ObjectMapper` 显式塞进 WebClient 的 codec；
二是**契约上就不传时间对象**，Java 侧格式化成 `yyyy-MM-dd` / `yyyy-MM-dd HH:mm` 字符串再下发。
后者更根本——契约明确、模型读 `2026-09-15 10:00` 比读 `2026-09-15T10:00:00` 更不容易理解错，
而且这类 Jackson 配置差异再也影响不到接口。

### 落库放在 doFinally + 专用线程池

`doFinally` 在流终止（完成/出错/客户端断开）时都会执行，保证「问过的问题一定留痕」。
JDBC 是阻塞操作，丢到 `aiDbExecutor`（有界队列 + CallerRunsPolicy）上跑，
不占用 Reactor 事件循环线程（Reactor 线程数 = CPU 核数，阻塞一个就少一个）。

### 用户上下文是裁剪过的

车辆 5 台、订单 5 笔、每笔 3 个明细、券 10 张。全量下发会让 prompt 膨胀到几万 token，
既慢又贵，而模型实际只需要「近期上下文」。这些上限都在 `carcare.ai.*` 配置里可调。

## 六、模型行为上的两个坑

### 1. 模型不知道今天是几号

用户说「这周六上午去」，模型会凭训练语料的记忆编一个过去的日期——
实测编出了 `2026-06-27`，而当天是 `2026-09-24`，生成的预约草稿是无效时间。

修法：用 `dynamic_prompt` 中间件在系统提示词里注入当天日期和星期。

**为什么用中间件而不是写进提示词常量**：常量在进程启动时就固定了，
长驻的服务第二天就会带着昨天的日期回答。

### 2. 工具调太多，把预算用完

一次预约咨询模型能连调 6 个工具（门店、项目、车辆、已领券、可抢券、出草稿），
把 4 次模型调用预算耗尽，中间件直接收尾，模型没机会写最终回答——
用户看到一堆工具调用成功，最后被告知「抱歉，这次没能生成有效回答」。

三处修：

1. **放宽轮数**：`MAX_TOOL_ROUNDS` 从 3 提到 5（依据是实测一次完整预约要用 4 轮，再留 1 轮收尾）；
2. **约束过度查询**：提示词里加「一次回答最多调用 3 个工具，用户没问的不要主动查——
   他没提优惠券就别查券」。加完后同场景工具调用从 6 次降到 3 次；
3. **兜底文案按「拿到了什么」分档**：有草稿就说「草稿已生成，请确认」，
   有工具结果就说「查到了但没整理成完整回答」，什么都没有才说抱歉。
   **草稿都出来了还说抱歉，用户会以为没成功。**

## 八、并发实测（阶段 8 收尾）

完整数据与复测命令见 [`performance-report.md` 第六节](performance-report.md)。
这里只记与设计相关的结论和两个方法论上的坑。

### 结论

| 问题 | 结论 |
|---|---|
| 并发下会断流吗 | 不会。100 并发 SSE 全部拿到 `done` 帧，0 错误 |
| 会丢数据吗 | 不会。495 次请求 → 495 条会话、990 条消息，零丢失；`message_count` 与实际消息数全部相符 |
| 自调用会死锁吗 | 不会。50 并发带工具的问题里，Python 回调 Java 内部接口全部正常返回 |
| 瓶颈在哪 | 上游大模型。模型调用自身从 1.1 s 涨到 2.6 s（p90 4.5 s），而这条链路上没有 Java |
| Java 层代价 | 50 并发下约 328 ms/请求（≈12%），加性成本，非扩展瓶颈 |

1~20 并发几乎零退化（1441 → 1520 ms），50 并发起明显上升。**全程 0 错误**，
Java 与 Python 两侧日志在压测窗口内 WARN/ERROR 均为 0（唯一一条 ERROR 是我自己
调试时路径写错导致的 404），也没有出现 Hikari 连接池超时或线程池拒绝。

### 坑一：判断「谁在排队」要看离散度，不能只看均值

50 并发时最大/最小 = 1.20——**连最快的那次请求也从 1.4 s 涨到了 4.3 s**。
本地资源排队（连接池占满、线程不够）会呈现「先到的快、后到的排长队」的长尾分布，
离散度必然拉大；所有请求被**均匀**拖慢才是上游吞吐受限的特征。这一列比均值有用得多。

### 坑二：上游 RT 会漂移，跨批次对比是无效的

同一配置前后两次跑，Java 侧均值 3733 ms vs 3062 ms，自己就差了 671 ms。
所以「Java 网关 vs 直连 Python」必须**交替跑**（A→B→A→B）再配对相减，
否则测出来的层间差异会直接混进上游漂移里。去掉首轮的预热偏离后，
4 对配对差值为 +333 / +265 / +386 ms，这才敢说 Java 层大约加了 328 ms。

### 附带发现的工具链坑

**Git Bash 的 MSYS 路径转换会把 JMeter 参数改掉**：`-Jpath=/v1/chat` 被自动改写成
`D:/study_xue/Git/v1/chat`，请求 404 且**不报参数错误**，只看 JMeter 汇总会误以为是服务问题。
在 Git Bash 里跑要加 `MSYS_NO_PATHCONV=1`，或者用 cmd。同类坑还有：命令行传中文会被
Git Bash 与 JVM 二次编码，中文问题要用 JSON 的 `\uXXXX` 转义形式传。

## 九、如果继续做

按优先级：

1. **限流与成本核算**。现在 `done` 事件带回了 token 数和耗时并落库，但没人汇总。
   补一个按用户/按天的聚合 + 配额，公网部署前必须做。
2. **强制收尾轮**。工具轮数用满时，与其靠兜底文案，不如再给模型一轮「必须现在回答」的强制指令。
3. **上探并发上限**。本轮验证到 100 并发仍 0 错误就停了，**「上限是多少」仍然未知**；
   要补多实例 + 网关层，并测出第一个出错点。
4. **知识库自动化**。从工单备注、评价内容里挖掘高频问题补充语料，而不是全靠手写。
5. **后台运营助手**。同一套 Python 服务 + 一套 admin 侧上下文，工具集换成经营数据查询。
