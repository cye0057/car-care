## 三、概念速查

### 3.1 为什么 Redis 是单线程，Lua 为什么能原子

**Redis 单线程**指的是它的**命令执行**是单线程的（I/O 是多线程的）。这个设计的好处是：**不需要锁**。如果命令是原子执行的，天然没有竞态。

**Lua 脚本**就是在 Redis 单线程里执行的，所以整个脚本作为一个整体运行，中间不会插入其他命令。这就是"原子"的来源——**不是加了锁，而是根本没有并发可能**。

```
客户端 A: EVAL "库存>0? 扣减+记名"  ← 执行期间
客户端 B: 无法插入任何命令           ← 必须等 A 的脚本跑完
```

对比分布式锁：你要**申请锁 → 执行 → 释放锁**，三次往返，而且锁有超时。Lua 没有锁这个概念，也就不存在"锁超时但业务还在跑"的经典 bug。

> **验证**：`resources/lua/seckill_voucher.lua` —— 一个脚本里完成「查库存 + 查重复 + 扣减 + 记名」四步。看看四步是怎么串起来的，没有任何锁调用。

### 3.2 Cache Aside 模式

最常见的缓存模式，记住**读写两条路径**就够了：

```
读：缓存 → 命中就返回；未命中 → 查 DB → 写缓存 → 返回
写：更新 DB → 删缓存（注意是删，不是更新）
```

**为什么写的时候删缓存而不是更新缓存？**
- 更新缓存浪费算力：很多数据写完之后根本没人读
- 并发写会互相覆盖，谁最后写谁赢，但写缓存的时机不一定和 DB 一致
- 删除是最简单的操作，且下次读会自然重建

### 3.3 穿透 / 击穿 / 雪崩（最容易混的三个词）

| 词 | 前提 | 现象 | 本项目对策 |
|---|---|---|---|
| **穿透** | key **从来不存在** | 每次请求都打穿到 DB | 空值也缓存（TTL 120s） |
| **击穿** | key **存在但过期了** | 热点 key 过期瞬间，并发全部打到 DB | 逻辑过期 + 互斥锁 |
| **雪崩** | **大量 key 同时**过期 | 整片缓存失效，DB 被瞬间打爆 | TTL 加随机抖动 |

**一句话区分**：穿透是「查不存在的东西」，击穿是「热点突然没了」，雪崩是「一大片同时没了」。

### 3.4 逻辑过期 vs 物理过期

```
物理过期：TTL 到点 → Redis 删掉 key → 下次读是 miss → 要回源重建
逻辑过期：TTL 给很长（7 天）→ key 永远在 → 数据里存个 expireAt
          → 读到 expireAt 已过期 → 直接返回旧值 + 异步重建
```

**逻辑过期的核心是「允许返回旧值」**。换来的是：过期瞬间不会有并发风暴打到 DB，200 个并发也只重建一次。

**什么时候不能用逻辑过期？** 库存、价格、余额——这些不能返回旧值的。那种场景直接用 Redis 存权威值，不走缓存一致性这套。

### 3.5 幂等的两种形态

幂等 = 同一操作执行一次和执行多次，结果一样。本项目用了两种，**适用场景不同**：

```
唯一索引幂等   → 防「重复插入」
               场景：MQ 重复投递同一条领券消息
               做法：INSERT 冲突 → 捕获异常 → 回补库存 → 吞掉

条件更新幂等   → 防「重复执行导致状态错乱」
               场景：库存扣减、订单状态流转
               做法：UPDATE ... SET stock = stock-1 WHERE stock > 0
```

**注意区别**：唯一索引靠的是「插入会失败」，条件更新靠的是「影响行数为 0」。前者挡重复写，后者挡非法状态转移。

### 3.6 死信交换机是怎么实现延迟消息的

这是最容易被问"到底怎么实现的"的点。原理：

```
delay.queue      ← 队列级 TTL = 10s，没有消费者
    │ 消息放进来，没人消费，就一直待着
    │ TTL 到期
    ▼
x-dead-letter-exchange  ← 队列声明时配了 x-dead-letter-exchange
    │ 过期消息被投到这个交换机
    ▼
close.queue      ← 真正有消费者在监听
```

**关键**：TTL 用**队列级**而不是**消息级**。消息级 TTL 有个坑——**队头阻塞**：如果队首消息还没过期，后续已过期的消息不会被检查，全堵在队头后面。队列级 TTL 所有消息统一过期时间，没有这个问题。

> **代码位置**：`config/RabbitConfig.java`（93 行），看 `delay.queue` 声明里的 `deadLetterExchange` 和 `ttl` 两个参数。

### 3.7 双游标分页 vs offset 分页

```
offset 分页：第 N 页 = 取 [N*5, N*5+5)
            问题：ZSet 上要按偏移量走，O(N)；且边界处理不好会重叠或漏

双游标分页：每次记录「上一页最后一条的 id」+「时间戳」
            下一页 = 取 id < 上一页最后 id 的前 5 条
            永远只查「比这个值小的」，O(logN + M)
```

**本项目的坑**（`FeedService` 里踩过两次）：
1. 初版用 `offset + score` 边界叠加 → 第二页把同一条记录跳过两次，返回空
2. 推/拉合并时同一笔记出现两次 → 合并层按 id 去重

**教训**：**用范围边界 + 游标时，边界是「包含」还是「排除」必须明确定义，并用测试锁死。** 这不是风格问题，是正确性问题。

### 3.8 推拉结合的写扩散/读扩散

```
推模式（写扩散）：发帖时，把内容写进每个粉丝的收件箱
                 写多读少。查询 O(1)，但发帖代价 ∝ 粉丝数

拉模式（读扩散）：发帖只写自己，查询时实时去拉被关注的人
                 写少读多。发帖 O(1)，但查询代价 ∝ 关注数
```

**为什么不能只用一种？**
- 纯推：百万粉大 V 发一条要写一百万次 ZSet，发帖就卡死了
- 纯拉：用户关注 500 个人，每次刷 Feed 要查 500 次 DB，查询慢

**本项目的做法**：按粉丝阈值自动切换。小账号推模式（普通用户查询零延迟），大账号拉模式（发帖 O(1)）。查询时两种来源合并去重。

**阈值 3000 是怎么定的？** 说实话是工程经验值，没有严格理论依据。真正的定法是做容量规划：算「ZADD 耗时 × 粉丝数」的写放大，找 P99 能接受的临界点。做成可配置项就是为了线上能调。

### 3.9 GEO 的底层是什么

Redis GEO 不是黑科技，底层就是 **GeoHash + ZSet**：

```
GeoHash：把经纬度编码成字符串前缀，前缀相同的点在地理上相邻
        例：120.16,30.27 → "wtmkn..." 

ZSet：   Score = 编码后的数值
        相近的点 Score 相近 → 按 Score 排序 ≈ 按地理位置排序

GEORADIUS：其实就是「找 Score 落在某个范围的元素」，
          再对结果做精确距离排序
```

**所以 GEO 查询的复杂度是 O(logN + M)**——logN 是 ZSet 的范围查找，M 是结果数量。

**踩过的坑**：`GeoResult.getDistance()` 的单位会随查询单位漂移，导致距离恒为 0。改成取回坐标后用 **haversine 公式**自算，单位确定且可测试。

### 3.10 ThreadLocal 与内存泄漏

```
每次请求 → 从线程池拿一个线程 → 把用户信息放进 ThreadLocal
                              ↓
线程池线程不销毁 → ThreadLocal 的 map entry 一直挂着
                              ↓
如果没有 remove() → 旧用户信息一直占内存，且下一个请求可能读到脏数据
```

**两个问题**：内存泄漏 + 数据串台。解法是在**拦截器的 `afterCompletion` 里显式 `remove()`**，保证请求结束就清理。

> **代码位置**：`common/BaseContext.java`（30 行）+ `config/LoginInterceptor.java`（61 行）。对照看 preHandle 存、afterCompletion 删。

### 3.11 JWT 为什么"无状态"，怎么登出

JWT 是**自包含**的：里面已经编码了用户身份，服务端不需要查数据库就能验证。**好处**是无状态，服务端不用存 session，天然支持多节点。**代价**是无法主动失效——签发出去了就收不回来。

**本项目怎么解决登出**：Redis 存一个黑名单，`logout:token:{jti}`，TTL = token 剩余有效期。拦截器校验时多查一次黑名单。代价是多一次 Redis 查询。

> **代码位置**：`utils/JwtUtil.java`（68 行）。

### 3.12 号段模式为什么快

```
自增 id：每发一个号 → 一次 DB 写  → 1000 个号 = 1000 次 DB 操作
UUID   ：不查 DB，但无序导致 B+ 树页随机插入、索引分裂
号段   ：一次取一段（步长 100）→ 本地内存发 100 个 → 1000 个号 = 10 次 DB 操作
```

**双缓冲 + 90% 预取**解决什么问题？「当前段用完了，要等下一次 DB 查询」的瞬间毛刺。做法：当前段用到 90% 时就**异步**去取下一段，取号的时候几乎不等待。

> **代码位置**：`service/SegmentService.java`（157 行）。

### 3.13 WebSocket 集群下的消息路由

**问题**：集群有 3 个节点，用户 A 的 WebSocket 连在节点 1，但新订单是节点 2 创建的。节点 2 怎么把消息送到节点 1 的会话？

**两种解法**：

```
会话粘滞：让网关保证「同一个用户永远路由到同一个节点」
         缺点：要网关配置粘性会话；节点重启/扩缩容后连接漂移就失效

Redis Pub/Sub 扇出（本项目）：
  节点 2 发布到 ws:notify
  → 所有节点都订阅了这个频道
  → 每个节点遍历自己持有的会话，只发给属于自己的
         优点：集群无关，新增节点自动加入，无需配置
```

**代价**：Redis 多一次扇出，且所有节点都会收到每条消息（即使和自己无关）。工单消息量很小，完全可接受。

**设计取舍**：通知是**尽力而为 + 列表兜底**。推送丢失不致命，用户刷新通知列表能看到。不追求推送的强可靠——那是即时通讯的需求，工单提醒不需要。

> **代码位置**：`service/WsNotifyService.java`（48 行，发布端）+ `websocket/WebSocketServer.java`（129 行，订阅与投递）。

### 3.14 为什么 `ServerEndpointExporter` 要求标 `@Component`

`@ServerEndpoint` 是标准 JSR-356 注解，**本身不会被 Spring 扫描**。`ServerEndpointExporter` 是 Spring Boot 提供的桥，它只把**Spring 容器里已经存在的 Bean** 注册到 WebSocket 容器。

所以少了 `@Component`，这个类压根不是 Bean，Exporter 就注册不了它 → 端点不存在 → 请求落到 MVC → 404 → 前端重连风暴。

**这个 bug 的隐蔽之处在于：它不抛异常，就是不生效。**

### 3.15 跨边界传输的字符集

`new String(bytes)` 会用 **JVM 默认字符集**解码。在 Windows 上默认是 GBK，但 UTF-8 编码的中文被 GBK 解码就会乱码。

**教训**：任何跨边界的数据（MQ 消息、Redis 值、HTTP body、WebSocket 帧）都要**显式指定字符集**，不要依赖 JVM 默认值。这也是为什么本项目代码里到处是 `StandardCharsets.UTF_8`。

### 3.16 后端中转上传（OSS）是什么

**问题**：图片文件放哪、怎么存？
**方案**：本项目走后端中转——前端 multipart POST 到 `/api/upload`，服务端校验后调阿里云 OSS SDK 的 `putObject`，返回公网 URL，前端只存 URL。对比前端直传（浏览器拿 STS 临时凭证直接传 OSS）：直传省服务器流量但要额外做 STS 签发与桶权限策略；中转把鉴权（复用登录拦截）、类型/大小校验、命名策略（`car-care/yyyy/MM/uuid.ext`）都收在服务端，毕设规模更可控。

**动手验证**：管理台门店编辑里传一张封面图，看 `t_store.cover` 落的是不是 `https://mycy-java.oss-cn-beijing.aliyuncs.com/...` 格式；浏览器直接打开该 URL 能访问说明 bucket 公共读已生效。代码位置：`UploadController`（校验+命名）、`OssUploader`（putObject 封装）。

### 3.17 支付宝回调为什么能信（验签 + 幂等）

**问题**：用户付完钱，服务端怎么安全地知道？
**方案**：不能信前端跳转结果，只信**异步回调**。支付宝服务器 POST 通知到 `notify_url`，我们做三件事：
1. **验签**：`AlipaySignature.rsaCheckV1(params, 支付宝公钥, "UTF-8", "RSA2")`——通知带了支付宝私钥的签名，验不过就是伪造，返回 `failure`；
2. **看状态**：`trade_status == TRADE_SUCCESS` 才算支付成功；
3. **幂等落库**：按 `out_trade_no` 查订单，已支付直接忽略，防止重复通知重复扣状态。

回调路径（`/api/notify/**`）必须放行登录拦截——支付宝没有我们的 JWT，安全性完全由验签承担。**动手验证**：沙箱控制台配置回调地址后，用沙箱买家账号付款，观察后端日志 `支付宝支付成功 out_trade_no=...`；手动重复 POST 同一通知体，订单时间不会被重复覆盖。

## 四、逐点深潜（原理 → 代码 → 验证 → 误解）

### 4.1 缓存击穿

**原理**：热点 key 过期瞬间，200 个请求同时 miss，全部打到 DB 重建。DB 被打爆。

**本项目代码**：
- `common/CacheData.java`（20 行）—— 缓存值的包装，内嵌 `expireAt`
- `common/CacheHelper.java`（80 行）—— SETNX 互斥锁 + Lua 安全解锁 + 延迟双删

**关键设计**：逻辑过期扛住 99% 的击穿，SETNX 互斥锁兜底重建并发，物理 TTL 7 天是最后防线。

**动手验证**：
```bash
# 1. 读一次热点接口，让它进缓存
curl --noproxy '*' http://localhost:8082/api/admin/stores/1

# 2. 删掉缓存 key
redis-cli -h 192.168.1.4 DEL "cache:store:1"

# 3. 立刻并发请求 200 次（用 JMeter breakdown 脚本）
# 预期：DB 只回源 2 次，其余 198 次拿到旧值或空转
```

**常见误解**：「互斥锁阻塞等待也是好的方案」。不是——200 个线程同时阻塞，RT 会被拖到重建耗时。本项目的实测是均值 13ms / P95 90ms，那个 P95 尖峰就是阻塞的代价。

### 4.2 延迟双删

**原理**：解决「写事务回滚前回填旧值」的竞态。

**时序图**（一定要画一遍）：
```
T1  读请求 miss，回源 DB，读到旧值 V1
T2  写事务提交 V2，删缓存
T3  写事务回滚（因为某个异常）
T4  T1 把 V1 写回缓存     ← 缓存里是旧值，DB 里也是旧值，看起来"一致"但 V2 丢了
T5  延迟 500ms 后再删一次   ← 清掉 T4 写入的脏值
```

**本项目代码**：`common/CacheHelper.java`，双删间隔 500ms。

**动手验证**：
```bash
# 改配置观察双删间隔
# application.yml: carcare.cache.ttl-seconds 可以调，但双删间隔是代码常量 500ms
# 找到 CacheHelper 里的延迟删除代码，看它是用 ScheduledExecutor 还是 @Async
```

**常见误解**：「双删能保证一致性」。不能——它假设第二次删除能追上回填。如果写事务耗时超过 500ms，就失效了。要强一致得上 Canal 监听 binlog。

### 4.3 秒杀三道闸门

**原理**：单点防护一定会失效，所以层层收窄。

**本项目代码**：
- `resources/lua/seckill_voucher.lua` —— 第 1 道，Lua 原子预减
- `t_coupon_order` 唯一索引 `(coupon_id, user_id, type)` —— 第 2 道
- `UPDATE t_coupon SET stock = stock-1 WHERE id=? AND stock > 0` —— 第 3 道
- `service/VoucherSeckillService.java`（183 行）—— 编排

**动手验证**：
```bash
# 1. 重置库存（管理台有重置接口）
# 2. 看 Redis 里的库存值
redis-cli -h 192.168.1.4 GET "seckill:stock:1"
# 3. 抢一张券
curl --noproxy '*' -X POST http://localhost:8082/api/seckill/coupons/1 -H "token: $TOK"
# 4. 再抢一次同一张 —— 预期返回"已领取过"，且 Redis 库存不再减少
# 5. 看 Lua 脚本的每一步判断，对应到返回码
```

**常见误解**：「有三道闸门就绝对安全」。不是——三道闸门是**降低失效概率**，不是消除。真正的最后一道是 DB 的条件更新，它不依赖 Redis 可用。

### 4.4 MQ 异步落库与幂等

**原理**：削峰 + 解耦。抢券成功不必等落库。

**本项目代码**：
- `config/RabbitConfig.java`（93 行）—— 交换机/队列声明
- `listener/SeckillConsumer.java` —— 消费端，手动 ack
- `service/VoucherSeckillService.java` —— 生产端

**动手验证**（需要先起 RabbitMQ）：
```bash
# 起 RabbitMQ 后，看队列状态
rabbitmqctl list_queues
# 抢一张券，立刻看队列深度是否增加
# 再等 1 秒，看是否被消费（深度降回 0）
# 打开 RabbitMQ 管理台 15672 可以看到实时消费
```

**常见误解**：「手动 ack 就够了」。不够——如果 ack 之后进程崩了，消息就丢了。要工业级得加本地消息表保证「发成功 + 落库成功」原子。这是本项目承认的不足。

### 4.5 死信延迟关单

**原理**：用「TTL 到期 → 死信」代替「定时扫表」。

**本项目代码**：`config/RabbitConfig.java`，看 `delay.queue` 的 `ttl` 和 `deadLetterExchange` 两个参数。

**动手验证**：
```bash
# 1. 当前 TTL 是 10s，下单
curl --noproxy '*' -X POST http://localhost:8082/api/orders \
  -H "token: $TOK" -H 'Content-Type: application/json' \
  -d '{"storeId":1,"itemId":1,"number":1}'
# 2. 立刻查订单状态，应该是 1（待支付）
# 3. 等 14 秒再查，应该是 5（已取消，超时未支付）
# 4. 改 application.yml 的 carcare.order.close-ttl-ms 为 5000，重启，
#    再试一次，观察关单时间缩短到约 9 秒
```

**常见误解**：「消息级 TTL 更方便」。更方便但有队头阻塞。单一超时时长用队列级 TTL，多个不同超时时长才需要考虑消息级或别的方案。

### 4.6 Feed 推拉切换

**原理**：按粉丝数自动选择写扩散或读扩散。

**本项目代码**：
- `service/FeedService.java`（114 行）—— 查询合并 + 双游标分页
- `service/FollowService.java` —— 阈值判断 `isBigAccount()`
- 配置 `carcare.feed.push-follower-threshold: 3000`

**动手验证**：
```bash
# 1. 正常发帖，看粉丝收件箱是否增加
redis-cli -h 192.168.1.4 ZCARD "feed:inbox:<粉丝uid>"

# 2. 把阈值改成 0（所有账号都算大 V → 全部拉模式）
#    application.yml: carcare.feed.push-follower-threshold: 0
# 3. 重启，再发帖
# 4. 观察收件箱条目数不变（推模式没生效）
# 5. 但 Feed 查询仍能返回这条笔记（拉模式生效）
# 这就是"双模式切换"的实测证据
```

**常见误解**：「推拉切换会导致数据重复」。会——本项目的真实 bug：阈值切换后同一笔记同时出现在收件箱和拉取结果。解决是合并层按 id 去重，不是靠切换逻辑。

### 4.7 GEO 写路径实时同步

**原理**：GEO 数据不能只靠启动装载，否则改了坐标不生效。

**本项目代码**：`service/GeoStoreService.java`（193 行）。门店新增/改坐标/转休息/删除都实时 `GEOADD`/`GEOREMOVE`。

```bash
# 4. 用附近门店接口查，距离应该变了
```

### 用 JMeter 做压测实验

脚本在 `document/jmeter/`，用 `-J` 参数化，不用改 `.jmx`：

```bash
JMX=D:/study_xue/JAVA_code/car-care/document/jmeter
JMETER=D:/study_xue/apache-jmeter-5.6.3/apache-jmeter-5.6.3/bin

# 缓存对比
del %JMX%\baseline-no-cache.jtl
%JMETER%\jmeter.bat -n -t %JMX%\store-detail-cache.jmx -JcacheEnabled=false -l %JMX%\baseline-no-cache.jtl

# 秒杀
del %JMX%\seckill-final.jtl
%JMETER%\jmeter.bat -n -t %JMX%\seckill-test.jmx -l %JMX%\seckill-final.jtl
```

**读 jtl 的方法**（这是压测的核心技能）：
```bash
python -c "
import csv, statistics as st
rows = list(csv.DictReader(open('result.jtl')))
el = [int(r['elapsed']) for r in rows]
ts = sorted(int(r['timeStamp']) for r in rows)
dur = (ts[-1]-ts[0])/1000 or 1
el_s = sorted(el)
pct = lambda p: el_s[min(int(p/100*len(el_s))-1, len(el_s)-1)]
print(f'请求 {len(el)} | 成功 {sum(1 for r in rows if r[\"success\"]==\"true\")} | QPS {len(el)/dur:.1f}')
print(f'RT 均值 {st.mean(el):.1f} | P50 {pct(50)} | P95 {pct(95)} | P99 {pct(99)} | 最大 {max(el)}')
"
```

**看什么**：
- **P99 比均值更重要**——均值会掩盖长尾，用户实际体感的是 P99
- **成功数必须核对业务语义**——秒杀的 `success=false` 是"没抢到"（正常），不是失败
- **`.jtl` 是追加写**——重跑前必须删，否则数据混入。这是本项目踩过的真实坑
