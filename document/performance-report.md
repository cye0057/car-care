# 全链路压测报告

> 环境：本机 Windows + JDK17 + Spring Boot 3.5，MySQL 8 / Redis 8.8 / RabbitMQ 3.13.7 均为**本地进程部署**
> 工具：JMeter 5.6.3 ｜ 数据文件：`document/jmeter/*.jtl`（原始样本，可复算）
> 数据日期：2026-09-15 ~ 2026-09-16（阶段 1~5）｜ 2026-09-24（阶段 8 AI 助手）

---

## 〇、必须先读的方法论说明

**本报告的价值在「正确性」和「数据库读保护」，不在 RT 数字。** 三点限制如实交代，避免误读：

1. **本地 MySQL 主键查询本身 <1ms**，因此「关缓存 vs 开缓存」的响应时间差异只有毫秒级，肉眼难辨。**缓存的核心价值是保护数据库**，本报告用「数据库实际执行的 SELECT 次数」而非 RT 来证明。
2. **不同脚本的线程数/循环次数不同**，QPS 只能在「同请求数」的两两之间比较，跨脚本横向比较无意义。
3. **`.jtl` 是追加写**，重跑前未删除旧文件会导致数据混入（早期一次压测就因此误判过）。所有结论均基于已清理的干净样本。

## 一、缓存体系（阶段 1）

### 1.1 数据库读保护 —— 核心指标

压测期间在 MySQL 开启 general log，统计实际执行的 `SELECT` 条数：

| 场景 | 请求数 | 关缓存 DB SELECT | 开缓存 DB SELECT | 降幅 |
|---|---|---|---|---|
| 热点详情（`/api/admin/stores/1`） | 5000 | 5001 | **1** | 99.98% |
| 穿透恶意 id（不存在的 id） | 5000 | 5000 | **1** | 99.98% |
| 击穿：删 key 后 200 并发同打 | 200 | ~200 | **2** | 互斥锁生效 |

5000 个请求只产生 1 次回源查询——**读放大降低 99.98%**。击穿场景「2」而非「1」，正是逻辑过期设计预期：旧值仍在有效期内时并发读直接返回旧值，仅 1~2 个线程负责重建。

### 1.2 吞吐对比

| 样本文件 | 请求数 | 总耗时 | 吞吐 (QPS) | 均值 RT | P95 | P99 | 最大 |
|---|---|---|---|---|---|---|---|
| `baseline-no-cache.jtl`（关缓存） | 5000 | 9.84 s | 508.0 | 1.2 ms | 3 ms | 4 ms | 91 ms |
| `cached-hot.jtl`（开缓存） | 5000 | 4.91 s | **1017.7** | 1.7 ms | 4 ms | 6 ms | 53 ms |

**同样 5000 个请求，开缓存后总耗时缩短一半，吞吐提升 2.0x**（508 → 1018 QPS）。

> 注意均值 RT 从 1.2ms 微升到 1.7ms：这是走 Redis 的额外开销，本地回环下远小于 MySQL 往返，属于合理代价。真正收益体现在总耗时与数据库负载上，**不能只看单请求 RT**。

### 1.3 击穿实验（互斥锁验证）

`breakdown.jtl`：删除缓存 key 后 200 并发同时请求同一热点 id。

| 指标 | 数值 |
|---|---|
| 请求数 | 200 |
| 吞吐 | 223.2 QPS（总耗时 0.90 s） |
| 均值 RT / P50 | 13.1 ms / 3 ms |
| P95 / P99 / 最大 | 90 ms / 91 ms / 91 ms |
| DB SELECT | 2 次 |

200 个并发只有 2 次回源，其余全部命中重建中的值或 SETNX 空转返回旧值——**互斥锁把击穿从「200 次 DB 查询」压到「2 次」**。P95 陡增到 90ms 正是持锁线程重建缓存、其余线程自旋等待的代价，属于设计预期。

## 二、优惠券秒杀（阶段 2）

秒杀的正确性远比吞吐重要。判定标准：**不超卖、不重复领、不丢失**。

### 2.1 终验（修复后）

`seckill-final.jtl`：冷启动，300 并发抢 20 库存。

| 指标 | 数值 | 判定 |
|---|---|---|
| 请求数 / 成功数 | 300 / **20** | ✅ 恰好等于库存 |
| 吞吐 | 339.8 QPS | 总耗时 0.88 s |
| 均值 RT / P50 | 9.6 ms / 4 ms | |
| P95 / P99 / 最大 | 10 ms / 210 ms / 215 ms | |
| DB 剩余库存 | 0 | ✅ 无超卖 |
| 领券记录条数 / 去重用户数 | 20 / 20 | ✅ 无重复领取 |
| 号段订单号 | 1001 ~ 1041 递增 | ✅ 无冲突 |

售罄后 Redis 库存归 0，后续请求由 Lua 直接拦截，**不再触达数据库**。P99 210ms 的长尾来自 20 个成功请求的「发号 + MQ 投递」路径，280 个失败请求在 Lua 内毫秒级返回。

### 2.2 修复前（`seckill-run.jtl`）—— 一次真实 bug 的压测证据

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 成功数 | **13** | 20 |
| 均值 RT / P99 / 最大 | 15.4 ms / 291 ms / 474 ms | 9.6 ms / 210 ms / 215 ms |

**压测实测丢了 7 个请求**（20 − 13 = 7）。根因：库存初始化用互斥锁，未抢到锁的线程空手返回，导致 Lua 把「key 不存在」误判为售罄。修复为 `setIfAbsent` 原子装载后，冷启动并发验证 20/20 无丢失。

> 这条数据是本项目最有价值的一类证据：**只有并发压测才暴露的竞态，单线程功能测试永远测不出来。**

## 六、AI 助手 SSE 长连接并发（阶段 8）

AI 助手是**长连接流式**接口，与前面几节的短请求性质不同：一个请求会占住连接几秒钟，
中间还要回调 Java 的内部接口取门店数据。这轮要回答两个问题：**并发下会不会断流/丢写**，
以及**瓶颈在哪一层**。

脚本：`document/jmeter/ai-chat-test.jmx`（目标可参数化，同一份脚本可打 Java 网关或直连 Python）。

### 6.1 梯度并发（打 Java 网关，轻问题「你好，你能做什么？」）

| 样本文件 | 并发 | 样本 | 错误 | 均值 RT | P50 | P90 | P99 | 最小 | 最大 | 离散度(max/min) |
|---|---|---|---|---|---|---|---|---|---|---|
| `ai-sanity.jtl` | 1 | 1 | 0 | 1540 ms | 1540 | 1540 | 1540 | 1540 | 1540 | 1.00 |
| `ai-light-5.jtl` | 5 | 5 | 0 | 1441 ms | 1403 | 1539 | 1539 | 1358 | 1539 | 1.13 |
| `ai-light-20.jtl` | 20 | 20 | 0 | 1520 ms | 1510 | 1758 | 1782 | 1334 | 1782 | 1.34 |
| `ai-light-50.jtl` | 50 | 50 | 0 | 4791 ms | 4794 | 5158 | 5182 | 4323 | 5182 | 1.20 |
| `ai-light-100.jtl` | 100 | 100 | 0 | 5584 ms | 5564 | 6269 | 6644 | 4801 | 6644 | 1.38 |
| `ai-tool-20.jtl` | 20（带工具） | 20 | 0 | 1882 ms | 1821 | 2444 | 2893 | 1372 | 2893 | 2.11 |
| `ai-tool-50.jtl` | 50（带工具） | 50 | 0 | 4257 ms | 4236 | 4774 | 5353 | 3447 | 5353 | 1.55 |

**1 ~ 20 并发几乎零退化**（1441 → 1520 ms），说明 Java 侧在这个量级没有任何排队。
50 并发开始明显上升，100 并发到 5.6 s，**但全程 0 错误、0 断流**。

**离散度这一列是判断「谁在排队」的关键**。50 并发时最大/最小只有 1.20——
连最快的那次请求也从 1.4 s 涨到了 4.3 s。如果是本地资源排队（连接池被占满、线程池不够），
会呈现「先到的快、后到的排长队」的**长尾**分布，离散度必然拉大。
所有请求被**均匀**拖慢，是上游吞吐受限的典型特征。

### 6.2 交叉对照：Java 网关 vs 直连 Python

同一份脚本、同样 `ramp=1`、同样问题，只改目标地址，交替跑 4 轮：

| 轮次 | A：Java 网关 | B：直连 Python | 差值 A−B |
|---|---|---|---|
| 1 | 3733 ms | 2761 ms | +972 ms |
| 2 | 3170 ms | 2837 ms | +333 ms |
| 3 | 3139 ms | 2874 ms | +265 ms |
| 4 | 3062 ms | 2676 ms | +386 ms |

> **为什么必须交替跑**：同一配置前后两次跑（3733 vs 3062）自己就差了 671 ms，
> 说明上游大模型的负载在分钟级漂移。不交替的话，测出来的「层间差异」会直接混进漂移里。

去掉首轮（JIT 与连接池预热，明显偏离其余三轮）：Java 均值 **3124 ms**，
直连 Python 均值 **2796 ms**，**Java 层引入约 328 ms（≈12%）**。

这 328 ms 是每请求一次的固定成本，不是随并发放大的墙：JWT 校验 → 读历史 →
组装用户上下文（车辆/订单/工单/券共 4~8 次查询，走 Hikari 默认 10 连接池）→ 落库。
它是**加性**的，量级与「模型调用本身 2.6 s」不在一个数量级。

### 6.3 瓶颈定位：直接测模型调用耗时

Python 的 `TimingMiddleware` 会把每次模型调用的耗时写进日志。这个数字**完全在 Java 之外测量**，
可以直接证伪「是不是 Java 拖慢的」：

| 阶段 | 模型调用样本 | 均值 | P50 | P90 | 最大 |
|---|---|---|---|---|---|
| 压测前（单请求探针） | 13 | 985 ~ 1479 ms | — | — | 1555 ms |
| 压测中 19:26（含 50/100 并发） | 215 | 2711 ms | 3041 | 4480 | 5146 ms |
| 压测中 19:28 | 121 | 2689 ms | 2727 | 3339 | 3609 ms |
| 压测中 19:30（交叉 A/B） | 352 | 2597 ms | 2559 | 3171 | 3866 ms |
| 压测中 19:32（交叉 A/B + 工具） | 150 | 1776 ms | 1836 | 2375 | 2795 ms |

**模型调用自己就从 ~1.1 s 涨到了 ~2.6 s**（p90 到 4.5 s），而这条链路上没有 Java。
结论明确：**延迟大头是 DeepSeek 在并发下的响应变慢，不是本项目的代码**。
Java 的 328 ms 与它相比是次要项，Python 的 RAG/工具编排也只在带工具的问题里才明显
（`ai-tool-50` 比 `ai-light-50` 多约 1 s，对应多一轮模型调用 + 知识库检索 + 目录接口回调）。

### 6.4 正确性验证（比 RT 更重要）

并发压测最容易暴露的是「看着成功、实际丢数据」。三项核对：

| 验证项 | 期望 | 实测 | 判定 |
|---|---|---|---|
| 会话落库 | 495 次请求 → 495 条 | **519 − 24 = 495** | ✅ 零丢失 |
| 消息落库 | 495 × 2 → 990 条 | **1043 − 53 = 990** | ✅ 零丢失 |
| `message_count` 与实际消息数一致性 | 全部相符 | 不符会话数 = **0** | ✅ |
| Java 日志（压测窗口 27372 行） | 无异常 | WARN **0**，ERROR **1** | ✅（那 1 条见下） |
| Python 日志（压测窗口 2517 行） | 无异常 | WARN **0**，ERROR **0**，Traceback **0** | ✅ |
| Hikari 连接池超时 / 线程池拒绝 | 无 | 关键字命中 **0** | ✅ |

那唯一的 1 条 ERROR 是 `NoResourceFoundException: No static resource v1/chat`——
我自己调试时被 Git Bash 的 MSYS 路径转换把 `-Jpath=/v1/chat` 改写成了 `D:/study_xue/Git/v1/chat`
导致的一次 404，与压测本身无关。**这条留着不删**，因为它记录了一个真实的踩坑。

另外核对了「有 user 消息但无 assistant 回复」的孤儿会话，共 3 条，
时间戳全在 17:32~17:52（浏览器里测「停止」按钮中断流留下的，属预期行为），
**压测窗口（19:24 之后）零孤儿**——异步落库在 100 并发下没有丢写。

### 6.5 这轮压测的结论

| 问题 | 结论 |
|---|---|
| 并发下会断流吗 | 不会。100 并发 SSE 全部拿到 `done` 帧，0 错误 |
| 会丢数据吗 | 不会。495/495 会话、990/990 消息，零丢失 |
| 自调用会死锁吗 | 不会。50 并发带工具的问题里，Python 回调 Java 内部接口全部正常返回 |
| 瓶颈在哪 | 上游大模型。模型调用自身 1.1 s → 2.6 s，均匀拖慢而非长尾排队 |
| Java 层代价 | 50 并发下约 328 ms/请求（≈12%），加性成本，非扩展瓶颈 |

**诚实的边界**：① 上游是共享的第三方 API，绝对 RT 随其负载漂移，本报告的数字用于**定性归因**
（谁在排队、会不会丢），不适合当作容量承诺；② 本地单机、Python 单实例，
没测多实例 + 网关层；③ 100 并发是本次验证到的上限，未继续上探到出错点，
所以**「上限是多少」仍然未知**；④ 没有做限流，公网部署前必须先补。

## 七、结论

| 维度 | 结果 |
|---|---|
| 数据库读保护 | 5000 请求 5001 次 SELECT → 1 次，**降幅 99.98%** |
| 缓存吞吐 | 同请求数下吞吐 **2.0x**，总耗时减半 |
| 击穿 | 200 并发的 200 次回源压到 2 次 |
| 秒杀正确性 | 300 并发抢 20 库存：**0 超卖、0 重复、0 丢失** |
| Feed 分页 | 翻页无重叠无丢失；推拉双模式实测切换 |
| AI SSE 并发 | 100 并发长连接 **0 断流 0 丢失**；瓶颈定位于上游模型（1.1 s → 2.6 s） |

**诚实的边界**：本环境为单机本地部署，MySQL/Redis/RabbitMQ 均为本地进程，无网络抖动与真实集群压力。数据用于证明**方案的正确性与读保护效果**，不能直接外推为生产集群容量。生产环境需补：多实例水平扩展、真实网络延迟、慢 SQL 场景、Redis 集群模式下的 Lua 槽位约束。

AI 一节另有其专属边界（见 6.5）：上游是共享第三方 API、绝对 RT 会漂移、未上探到出错点。
